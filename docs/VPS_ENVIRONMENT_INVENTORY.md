# VPS Environment Variable Inventory

Phase 0 output for the Manus/Cloud → VPS (Coolify + MariaDB) migration. Built entirely from a source-code audit (`rg -n "process\.env|import\.meta\.env|ENV\."` across `client server scripts shared drizzle.config.* package.json`, plus reading `server/_core/env.ts` in full as the authoritative central config). **No secret values appear anywhere in this document** — names and behavior only.

Audited at repo HEAD `da3a65e16b51ed7e81cead6fd3559e444fd3a814` (origin/main).

## How to read this table

- **Build/Runtime**: *Build* = baked into the client bundle at `vite build` time (`import.meta.env.VITE_*` or an `index.html` `%VAR%` substitution) and cannot be changed without a rebuild. *Runtime* = read by the Node server process from `process.env` on every boot/request and can be changed by restarting the container.
- **Secret/Public**: *Secret* = must never be logged, committed, or exposed client-side. *Public* = safe to appear in the client bundle or logs.
- **Required/Optional**: *Required* = the app throws, refuses to start, or a core feature hard-fails without it. *Optional* = has a working default, or only degrades a specific feature.
- **VPS value source**: where the value should come from on the new VPS (Coolify's environment-variable UI, a secrets manager, or "same value as current production" if it isn't changing).
- **Verification method**: how to confirm it's set correctly *without* printing the secret — used by `scripts/vps-migration/preflight.mjs` (see that script) and the manual checklist.

## Minimum bar for "app can start"

`server/_core/healthCheck.ts`'s `getReadinessStatus()` treats exactly these four as hard-required: `DATABASE_URL`, `JWT_SECRET`, `VITE_APP_ID`, `OAUTH_SERVER_URL`. Everything else degrades a specific feature rather than blocking boot.

### Mandatory Google-Migration Gate (optional, `transition` or `google` mode)

An opt-in escalation on top of `transition`/`google` mode: instead of merely offering Google linking, these variables together FORCE it - existing sessions are invalidated (so a fresh, old-way login re-authenticates the real account), and every "business action" (bookshelf, wallet, points, orders, payments, purchases, wishlist, reading a member-only episode, editing profile data) is blocked, both client-side (a redirect to `/account/upgrade-login`) and, more importantly, server-side (every `protectedProcedure` tRPC call - see `server/_core/googleMigrationGate.ts`, wired centrally into `server/_core/trpc.ts`) until the signed-in user connects a Google identity. Admin sessions and admin-only procedures are never subject to any part of this - see `server/_core/trpc.ts`'s `adminProcedure`, which is built on `authenticatedProcedure`, never `protectedProcedure`.

`AUTH_REQUIRE_GOOGLE_CONNECTION_AFTER` layers a **targeted, scheduled cutoff** on top: when set, the gate is `enabled` immediately (banner shown, connect optional) but only becomes `activeNow` (blocking) once the server's own clock reaches that instant - see `server/_core/env.ts`'s `evaluateGoogleConnectionCutoff()`, the single source of truth both the server enforcement gate and the client status query (`auth.googleConnectionCutoffStatus`) defer to. The client never decides activation from its own clock.

#### Rollout Sequence

The mandatory gate is designed to be turned on in stages, not all at once:

1. **Deploy `transition` mode, not yet mandatory** - `AUTH_PROVIDER=transition`, `VITE_AUTH_PROVIDER=transition`, `AUTH_REQUIRE_GOOGLE_CONNECTION`/`VITE_AUTH_REQUIRE_GOOGLE_CONNECTION` both unset/`false`. Existing Manus logins are completely unaffected; users can optionally connect Google from `/profile`.
2. **Verify Google Connect works** - manually confirm the connect flow end to end on staging/production for a real account (see the Manual Staging Checklist in the PR description).
3. **Set `AUTH_FORCE_RELOGIN_AFTER`** to force a fresh old-way login for every existing session (re-establishing `iat` for real, currently-active users) - a one-time step; a past cutoff has no further effect on sessions created after it.
4. **Enable the gate, optionally with a scheduled (not immediate) cutoff** - set `AUTH_REQUIRE_GOOGLE_CONNECTION=true` and `VITE_AUTH_REQUIRE_GOOGLE_CONNECTION=true` (client rebuild required). Optionally also set `AUTH_REQUIRE_GOOGLE_CONNECTION_AFTER` to a future UTC timestamp to announce the cutoff ahead of time (banner shown, nothing blocked yet) instead of enforcing immediately.
5. **Give users time to migrate** - monitor for users stuck on `/account/upgrade-login` once the cutoff is reached; the "ติดต่อฝ่ายช่วยเหลือ" link (`VITE_SUPPORT_URL`) is their escape hatch if something goes wrong (e.g. an Apple Hide My Email edge case).
6. **Switch to `google`-only** later, once every remaining user has migrated - `AUTH_PROVIDER=google`, `VITE_AUTH_PROVIDER=google` (`AUTH_REQUIRE_GOOGLE_CONNECTION`/`AUTH_REQUIRE_GOOGLE_CONNECTION_AFTER` remain fully active under `google` mode too, unlike the old `transition`-only behavior - they only go inert under `manus`).

Turning the mandatory gate back OFF at any stage (`AUTH_REQUIRE_GOOGLE_CONNECTION=false`, `VITE_AUTH_REQUIRE_GOOGLE_CONNECTION=false`, rebuild the client) never damages any session or user data - it simply stops enforcing the requirement; every account, purchase, and identity link made while it was on remains exactly as it was.

### Deployment Matrix (`AUTH_PROVIDER` / `VITE_AUTH_PROVIDER`)

The server flag and the client flag are independent variables — always set them to the **same** value for a given environment; nothing derives one from the other, so a deploy that only updates one of the two fails closed to Manus rather than silently mixing flows.

| `AUTH_PROVIDER` (server) | `VITE_AUTH_PROVIDER` (client, build-time) | Manus callback (`/api/oauth/callback`) | Google login (`/api/auth/google/start`, `/callback`) | Google connect (`/api/auth/google/connect/start`) | Client "Sign in" buttons | Notes |
|---|---|---|---|---|---|---|
| `manus` | `manus` | Active | 404 | 404 | Manus OAuth URL, unchanged | Current production behavior — identical to before this feature existed |
| `google` | `google` | 404 | Active | Active (requires an existing session) | Google start path directly | Full cutover — matches merged PR #25 behavior exactly; no in-app `/login` page is used |
| `transition` | `transition` | Active | Active | Active (requires an existing session) | In-app `/login` page (both Manus and Google options) | The migration mode this feature adds — existing Manus users keep working unchanged and can additionally connect a Google identity from `/profile`'s "บัญชีที่เชื่อมต่อ" section |

Because `VITE_AUTH_PROVIDER` is baked into the client bundle at build time, switching between rows in this matrix always requires a client rebuild + redeploy, not just restarting the server container with a new `AUTH_PROVIDER` value. Rolling back is the same operation in reverse: set both variables back to `manus` and rebuild.

## OCR / LLM ("Forge" platform)

`LLM_API_URL`/`LLM_API_KEY`/`LLM_MODEL` (below) let `server/_core/llm.ts`'s `invokeLLM()` - and therefore OCR slip parsing - run against any operator-owned, OpenAI-compatible Chat Completions provider instead of Manus's internal Forge API, without touching the other Forge-dependent features (`storage.ts`, `dataApi.ts`, `imageGeneration.ts`, `notification.ts`, `voiceTranscription.ts`), which still only speak `BUILT_IN_FORGE_*` and are unaffected by this change. Resolution is centralized in `resolveLLMRuntimeConfig()` (`env.ts`'s job is only to expose the raw values) and is strictly one atomic set or the other, never a mix:

- **If ANY of `LLM_API_URL`/`LLM_API_KEY`/`LLM_MODEL` is set**, generic mode is selected and **all three are required** - a partial set throws a startup-safe (call-time, not boot-time) configuration error naming only the missing variable(s), and never silently falls back to `BUILT_IN_FORGE_*`.
- **Only when none of the three `LLM_*` vars are set** does OCR/LLM fall back to legacy Manus Forge behavior (`BUILT_IN_FORGE_API_KEY`, `BUILT_IN_FORGE_API_URL` or the `forge.manus.im` default, and the historical `gemini-2.5-flash` model) - unchanged, so existing Manus Production deployments need no configuration change at all.
- `LLM_API_URL` must be the **complete** chat-completions endpoint (e.g. `https://your-provider.example.com/v1/chat/completions`) - it is used exactly as given, never suffixed with `/v1/chat/completions`.

**Payment-slip images (OCR Vision) - transport differs by mode**, handled by `server/services/ocrImageInputService.ts`'s `prepareSlipImageForOcr()`, called by both `slipSubmissionService.ts` (order payments) and `walletTopupSubmissionService.ts` (wallet top-ups) immediately before every OCR call:

- **Legacy Forge (unchanged)**: private R2 ref → fresh signed URL → handed straight to Forge as `image_url.url`. No server-side download, no base64 conversion.
- **Generic mode**: a generic OpenAI-compatible provider was proven on staging to reject a private R2 signed HTTPS URL passed directly as `image_url.url` (`HTTP 400`) - the identical object, fetched server-side and sent as a base64 data URL, succeeds (`HTTP 200`). So in generic mode: private R2 ref → fresh signed URL → **server-side bounded fetch** → `data:<mime>;base64,...` → Vision call. The data URL is never stored, logged, or returned to the browser - it exists only transiently in memory for that one LLM call.
  - Server-side fetch limits: **5 MiB max** (matches the slip upload service's own ceiling; enforced from `Content-Length` *and* while streaming the body, never accumulated unbounded), a 10s timeout, and `redirect: "error"` (a server-generated presigned URL never needs to follow a redirect).
  - Only **JPEG/PNG** are sent to Vision - `application/pdf` (accepted by the upload service, but already manual-review-only) is never treated as an image.
  - **A legacy external absolute URL (not an `r2p:` reference) is never server-fetched in generic mode** - fetching an arbitrary stored URL server-side would be an SSRF primitive. Any preparation failure (fetch/timeout/size/MIME/legacy-URL/unconfigured-LLM) fails closed into the existing OCR technical-error → manual-review path (`pending_review` / `needs_review` / `OCR_PROCESSING_ERROR`) - never an auto-approval, credit, or crash.

## Known documentation drift (found while auditing)

- `OCR_AUTO_APPROVE_CONFIDENCE_THRESHOLD` is mentioned in `OCR_ACTIVE_PATH_HARDENING_REPORT.md` as a configuration example, but **no code anywhere reads this name** — the real variable is `OCR_MIN_CONFIDENCE`. Do not configure `OCR_AUTO_APPROVE_CONFIDENCE_THRESHOLD` on the VPS; it would silently do nothing.

## TLS / connection-string note for `DATABASE_URL` specifically

`server/db.ts`'s production DB connection (`getDb()`) sets **no explicit TLS options** — it relies entirely on whatever query-string parameters (if any) are present in `DATABASE_URL` itself. The current production TiDB Cloud connection almost certainly requires `?ssl={"rejectUnauthorized":true}`-style parameters or equivalent in the URL today. A self-hosted MariaDB reachable only over Coolify's internal Docker network **should not** need TLS at all — when constructing the new `DATABASE_URL` for the VPS, drop any TLS query parameters that assumed a public, TLS-required TiDB Cloud endpoint. See `docs/VPS_MIGRATION_RUNBOOK.md`'s database-compatibility section for detail on the internal-network TLS assumption already partially handled in test helpers (`testDbConnectionOptions.ts`) but **not yet in the production connection path** — this is flagged there as a "needs live MariaDB verification" item, not a blocker.
