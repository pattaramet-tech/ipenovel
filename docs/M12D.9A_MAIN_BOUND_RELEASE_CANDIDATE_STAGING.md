# M12D.9A — Main-Bound Release Candidate + Isolated Production Staging

## Objective

Insert a release-candidate staging boundary between development Preview and Production. A Production candidate must originate from `main`, run at an exact immutable SHA on an isolated Production-staging database, and pass the Full Playwright gate before M12D.9 may authorize Production activation.

The development Preview branch remains useful for integration, but `preview/promotion-eligibility` is no longer sufficient for Production promotion.

## Evidence chain

```text
main HEAD = X
→ Main Production Release Candidate workflow
→ production-staging/main-bound-rc = success
→ production-staging/rc-baseline/<baseline-sha> = success
→ ipenovel-production-staging pinned to X
→ DB identity guard passes before migrations
→ startup migrations complete on isolated staging DB
→ /readyz revision=X, environment=production-staging
→ production-staging-deployed repository_dispatch
→ Full Playwright gate 8/8
→ production-staging/release-candidate = success
→ production-staging/release-baseline/<baseline-sha> = success
→ M12D.9 may authorize X
```

## Main-bound RC creation

Workflow: `.github/workflows/main-release-candidate.yml`.

Inputs:

```text
candidate_sha=<full current main HEAD>
production_baseline_sha=<full current Production rollback SHA>
confirmation=CREATE_MAIN_RELEASE_CANDIDATE
```

The workflow fails unless the candidate equals `origin/main` HEAD at RC creation and the Production baseline is an ancestor of the candidate.

## Dedicated staging resource

Create a separate Coolify application:

```text
Name: ipenovel-production-staging
Repository: pattaramet-tech/ipenovel
Branch: main
Commit SHA: <main-bound RC SHA>
Auto deploy: Manual deployments only
Domain: https://production-staging.ipenovel.com
```

Do not reuse `ipenovel-preview` or `ipenovel-prod`.

## Isolated staging database guard

Production staging must set:

```text
DEPLOYMENT_ENVIRONMENT=production-staging
PRODUCTION_STAGING_DB_FINGERPRINT=<staging DB identity hash>
PRODUCTION_DB_FINGERPRINT=<Production DB identity hash>
```

Generate a database identity hash in a trusted environment where `DATABASE_URL` is already present:

```bash
pnpm database:identity
```

The helper hashes only protocol, hostname, port, and database name. Credentials and query parameters are excluded. Never paste database URLs into chat, GitHub inputs, logs, or source control.

`server/_core/productionStagingSafety.ts` runs before `ensureDatabaseMigrated()`. Startup fails before migrations if the staging fingerprint is missing, equals the Production fingerprint, if `DATABASE_URL` resolves to Production, or if `DATABASE_URL` does not match the approved staging identity.

Use a separate schema-compatible staging database prepared from the current Production baseline. Prefer a sanitized snapshot or schema-equivalent dataset with only regression-test records; do not expose an unsanitized Production data copy on a public staging domain.

## Runtime identity

Staging must report:

```json
{
  "status": "ready",
  "revision": "<candidate SHA>",
  "environment": "production-staging"
}
```

`/readyz.environment` is allowlisted to `preview`, `production-staging`, or `production`; arbitrary environment values are not reflected.

## Post-deploy dispatch

Staging runtime variables:

```text
GITHUB_PRODUCTION_STAGING_DISPATCH_TOKEN=<repo-scoped repository-dispatch token>
PRODUCTION_STAGING_BASELINE_SHA=<full baseline SHA>
```

Post-deployment payload must send:

```json
{
  "event_type": "production-staging-deployed",
  "client_payload": {
    "deployed_sha": "<SOURCE_COMMIT>",
    "baseline_sha": "<PRODUCTION_STAGING_BASELINE_SHA>",
    "environment": "production-staging",
    "source_branch": "main"
  }
}
```

## Staging regression workflow

Workflow: `.github/workflows/production-staging-regression.yml`.

Required repository secrets:

```text
E2E_PRODUCTION_STAGING_USER_STORAGE_STATE_B64
E2E_PRODUCTION_STAGING_ADMIN_STORAGE_STATE_B64
```

These storage states must be captured from the staging domain. Development Preview state is not reused.

Success records:

```text
production-staging/release-candidate = success
production-staging/release-baseline/<baseline-sha> = success
```

## M12D.9 integration

M12D.9 no longer accepts development Preview evidence. Production authorization requires the candidate to remain in `main` history, both staging statuses above, the main-bound RC status, matching staging revision/environment, the rollback ancestry check, Production backup/baseline confirmation, and migration review.

Production activation remains a separate explicit human-controlled step.

## Completion criteria

M12D.9A is complete only after a new post-merge `main` SHA is bound as an RC, deployed to the dedicated staging resource, started against the isolated staging DB, passes Full Gate 8/8, and is accepted by M12D.9 preflight simulation without activating Production.
