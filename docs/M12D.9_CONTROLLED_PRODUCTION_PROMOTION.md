# M12D.9 — Controlled Production Promotion

## Scope

M12D.9 authorizes and verifies an exact Production deployment after M12D.9A has produced a main-bound release candidate that passed isolated Production staging.

This infrastructure milestone is separate from `docs/workspace/M12D9_UNATTENDED_CONTROLLED_PUBLISH_WORKER.md`.

## Candidate source

Development Preview SHA `b2c8054c3c91e284408af02c608df354594de96a` is not a Production candidate because that branch contains Preview-only commits not present on `main`.

Production candidates must instead satisfy M12D.9A:

```text
production-staging/main-bound-rc = success
production-staging/release-candidate = success
production-staging/release-baseline/<rollback-sha> = success
```

and `https://production-staging.ipenovel.com/readyz` must report the exact candidate revision with `environment=production-staging`.

## Safety model

Production activation is split into three phases:

1. **Authorize** — `.github/workflows/production-promotion.yml` verifies main membership, isolated staging evidence, exact baseline binding, rollback ancestry, backup/baseline attestations, migration review, typecheck, build, and the repository release gate.
2. **Activate** — an operator manually pins `ipenovel-prod` to the exact authorized SHA in Coolify and starts a manual deployment. GitHub does not call the current HTTP-only Coolify API.
3. **Verify** — `repository_dispatch: production-deployed` runs `.github/workflows/production-deploy-verify.yml`, which verifies authorization, exact Production `/readyz.revision`, stable health/readiness, and a read-only HTML root smoke test.

Production auto-deploy remains disabled.

## Authorization inputs

Run `Controlled Production Promotion` from `main` with:

```text
candidate_sha=<M12D.9A staging-qualified main SHA>
rollback_sha=<full currently deployed Production SHA>
backup_confirmed=true
baseline_confirmed=true
migration_review_confirmed=true
confirmation=AUTHORIZE_PRODUCTION_PROMOTION
```

Configure repository variable:

```text
PRODUCTION_VITE_PAYMENT_QR_IMAGE_URL=<exact Production public HTTPS QR image URL>
```

The workflow records:

```text
production/promotion-authorization = pending|success|failure
```

`success` authorizes explicit deployment; it does not deploy Production.

## Preflight invariants

The preflight fails closed unless:

- candidate and rollback are full repository SHAs;
- rollback is an ancestor of candidate;
- candidate remains contained in current `main` history;
- candidate has successful `production-staging/main-bound-rc` evidence;
- candidate has successful isolated `production-staging/release-candidate` evidence;
- staging evidence is bound to the exact rollback SHA through `production-staging/release-baseline/<rollback-sha>`;
- staging `/readyz` reports the exact candidate and `environment=production-staging`;
- staging statuses point to the expected successful GitHub workflow runs;
- Production backup and current rollback baseline are explicitly confirmed;
- current Production revision matches rollback when revision metadata is available, otherwise the legacy Production branch HEAD must match rollback;
- destructive-looking migration operations require explicit migration-review confirmation.

## Production activation

After authorization succeeds, change only `ipenovel-prod`:

```text
Auto deploy: Manual deployments only
Commit SHA: <authorized candidate SHA>
```

Keep the full SHA pinned. Branch normalization is a separate follow-up; do not combine source-branch cleanup with the first controlled promotion.

## Production post-deploy hook

Set a runtime-only repository-dispatch token:

```text
GITHUB_PRODUCTION_DISPATCH_TOKEN=<repo-scoped repository-dispatch token>
```

Post-deployment dispatch payload:

```json
{
  "event_type": "production-deployed",
  "client_payload": {
    "deployed_sha": "<SOURCE_COMMIT>",
    "environment": "production"
  }
}
```

The Production verification workflow records:

```text
production/deployment-verification = success|failure
```

Verification is read-only; it performs no checkout, wallet, payment, slip, admin, or publishing mutation.

## Operator checks

Before activation:

```bash
pnpm production:promotion:check <candidate-sha>
```

Expected:

```text
STATE=success
AUTHORIZED=yes
```

After deployment, the candidate must show:

```text
production-staging/main-bound-rc = success
production-staging/release-candidate = success
production/promotion-authorization = success
production/deployment-verification = success
```

## Rollback

Capture the currently deployed Production SHA before activation. If deployment or verification fails, re-pin `ipenovel-prod` to that exact rollback SHA and deploy manually.

Startup migrations are not automatically reversed by a code rollback. A verified restorable database backup is therefore mandatory before authorization.

## Out of scope

- automatic Production deployment;
- automatic database rollback;
- Production auto-deploy;
- Production E2E mutation;
- source-branch normalization during the first controlled promotion.
