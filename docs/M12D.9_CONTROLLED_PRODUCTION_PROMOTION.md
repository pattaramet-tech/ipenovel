# M12D.9 — Controlled Production Promotion

## Scope

This deployment milestone converts a Preview-qualified SHA into an explicitly authorized Production candidate, then verifies the exact SHA after a human-controlled Coolify deployment.

This file is separate from `docs/workspace/M12D9_UNATTENDED_CONTROLLED_PUBLISH_WORKER.md`; that workspace milestone concerns the editorial publish worker, not infrastructure promotion.

## Current promotion candidate

- Preview candidate: `b2c8054c3c91e284408af02c608df354594de96a`
- Current legacy Production rollback baseline: `d90220bbdaeef53afdfe15bf83cc3b319aa75a62`
- The rollback baseline is an ancestor of the candidate.
- Delta at implementation time: 76 commits, 220 files.
- New migration files between those revisions: `0040` through `0054` (15 SQL files).
- The migration scanner flags `0051_workspace_editorial_multitab_stage.sql` because it drops the old `wees_approval_unique` index after adding the replacement `wees_approval_episode_unique(approvalId, episodeNumber)` unique constraint.

These values describe the first M12D.9 promotion only. The scripts are SHA-driven and do not hardcode them.

## Safety model

Production activation is deliberately split into three phases:

1. **Authorize** — GitHub Actions proves the exact candidate is still the current Preview HEAD, is actually live on Preview, has `preview/promotion-eligibility=success`, points to a successful `preview-deployed` repository-dispatch run, is a linear descendant of the rollback SHA, and has an explicitly reviewed migration delta.
2. **Activate** — an operator manually pins `ipenovel-prod` to the exact authorized commit SHA in Coolify and starts a manual deployment. GitHub Actions does not hold a Coolify API token and does not call the current HTTP-only Coolify API.
3. **Verify** — the Production post-deploy hook emits `repository_dispatch: production-deployed`; GitHub verifies the deployed SHA has `production/promotion-authorization=success`, then requires `/healthz` and `/readyz` to report healthy/ready with the exact SHA for three consecutive probes and performs a read-only HTML root smoke test.

Production auto-deploy remains disabled.

## Authorization workflow

Workflow: `.github/workflows/production-promotion.yml`

Before the first real authorization run, configure this GitHub **Repository Variable** (not a secret):

```text
PRODUCTION_VITE_PAYMENT_QR_IMAGE_URL=<the exact public HTTPS payment QR image URL used by Production>
```

The workflow deliberately fails if this variable is missing. The candidate's Vite production-build gate requires the real public build-time URL and rejects missing/non-HTTPS/legacy-Manus values; M12D.9 does not substitute a dummy URL.

Run only from `main` using `workflow_dispatch` with:

```text
candidate_sha = <full Preview-qualified SHA>
rollback_sha = <full currently deployed Production SHA>
backup_confirmed = true
baseline_confirmed = true
migration_review_confirmed = true
confirmation = AUTHORIZE_PRODUCTION_PROMOTION
```

The workflow creates `production-promotion-manifest.json`, typechecks and builds the exact candidate, runs the repository's existing `pnpm test:gate`, uploads the manifest for 30 days, and records this commit status on the candidate:

```text
production/promotion-authorization = success|failure|pending
```

`success` means the SHA is authorized for explicit Production activation. It does not deploy anything. Any new release-gate failure keeps authorization at `failure`; M12D.9 must never update the baseline merely to make a candidate pass.

## Preflight invariants

The preflight fails closed unless all of the following are true:

- candidate and rollback are full Git SHAs present in the repository;
- rollback is an ancestor of candidate;
- candidate equals current `origin/fix/m12d8-reconcile-056-ui` HEAD;
- Preview `/readyz.revision` equals candidate;
- candidate has latest `preview/promotion-eligibility=success`;
- that status points to a successful `repository_dispatch` run named `preview-deployed`;
- a restorable Production backup is explicitly confirmed;
- rollback baseline is explicitly confirmed;
- if current Production exposes a revision, it equals rollback;
- while Production is still legacy and exposes no revision, `origin/fix/ipe045-account-recovery-survivor-donor` must equal rollback;
- any destructive-looking migration operation requires explicit migration-review confirmation.

## Initial candidate gate result

During M12D.9 implementation, the exact candidate `b2c8054c3c91e284408af02c608df354594de96a` passed SHA/Preview/baseline/migration preflight simulation, but its existing repository release gate reported **36 failures not present in the recorded baseline**. Therefore this candidate is **not Production-authorized yet**. Production activation remains blocked until those failures are individually reconciled as real fixes or independently justified baseline debt.

## First Production activation

After authorization succeeds, configure only `ipenovel-prod` in Coolify:

```text
Auto deploy: Manual deployments only
Branch: fix/m12d8-reconcile-056-ui
Commit SHA: <authorized candidate SHA>
```

Changing the branch for this first promotion is necessary because the authorized candidate lives on the Preview integration branch while the current Production source branch still points at the legacy rollback commit. Keep the full commit SHA pinned; do not deploy branch HEAD implicitly.

Do not normalize Production to `main` in the same deployment. Source-branch normalization is a separate follow-up after the exact candidate has been proven live.

## Production post-deploy hook

Add a runtime-only secret on `ipenovel-prod`:

```text
GITHUB_PRODUCTION_DISPATCH_TOKEN=<repo-scoped fine-grained token capable of repository dispatch>
```

The existing Preview dispatch token may be reused if organizational policy permits, but use the Production-specific environment-variable name so the two paths remain auditable.

Set this Production Post-deployment command:

```bash
node -e "const sha=(process.env.SOURCE_COMMIT||'').trim();if(!/^[0-9a-f]{40}$/i.test(sha)){console.error('SOURCE_COMMIT missing or invalid');process.exit(1)};fetch('https://api.github.com/repos/pattaramet-tech/ipenovel/dispatches',{method:'POST',headers:{'Accept':'application/vnd.github+json','Authorization':'Bearer '+process.env.GITHUB_PRODUCTION_DISPATCH_TOKEN,'X-GitHub-Api-Version':'2022-11-28','Content-Type':'application/json'},body:JSON.stringify({event_type:'production-deployed',client_payload:{deployed_sha:sha,environment:'production'}})}).then(async r=>{if(!r.ok){console.error('dispatch failed',r.status,await r.text());process.exit(1)}console.log('production-deployed dispatch sent for '+sha)}).catch(e=>{console.error(e);process.exit(1)})"
```

Then Save and use Coolify's normal manual Deploy/Redeploy action.

## Post-deploy verification

Workflow: `.github/workflows/production-deploy-verify.yml`

The `production-deployed` dispatch starts verification automatically. Success records:

```text
production/deployment-verification = success
```

The verification path performs no checkout/payment/wallet/slip/admin/publishing mutation. It only reads GitHub status, `/healthz`, `/readyz`, and the Production root page.

## Operator checks

Authorization can be checked with:

```bash
pnpm production:promotion:check <candidate-sha>
```

Expected before activation:

```text
STATE=success
AUTHORIZED=yes
```

After deployment, the GitHub commit statuses must show both:

```text
preview/promotion-eligibility = success
production/promotion-authorization = success
production/deployment-verification = success
```

## Rollback

Rollback target must be captured before activation. For the first promotion it is the currently deployed legacy revision `d90220bbdaeef53afdfe15bf83cc3b319aa75a62`.

If the new deployment fails before becoming healthy, or post-deploy verification fails:

1. In `ipenovel-prod`, restore Branch to `fix/ipe045-account-recovery-survivor-donor`.
2. Set Commit SHA to the captured rollback SHA.
3. Keep Auto deploy as Manual deployments only.
4. Deploy manually.
5. Confirm `/healthz` and `/readyz` return healthy/ready.
6. Investigate schema/data state before any database restore. M12D.9 never performs an automatic database rollback.

Because startup migrations run before the candidate opens its port, a code rollback does not automatically reverse schema changes. A verified backup is therefore a mandatory precondition rather than an optional precaution.

## Out of scope

- Automatic Production deployment.
- Automatic database rollback.
- Production source-branch normalization to `main`.
- Any Production E2E mutation.
- Enabling Production auto-deploy.
